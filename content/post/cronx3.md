# Making Scheduled Jobs Observable

## Introduction

A scheduled job can fail in many different ways.
It may never start, terminate with an error, exceed its execution timeout, or complete successfully after several attempts. Sometimes the scheduler itself may stop unexpectedly, leaving the outcome of an execution uncertain.
The difficult part is not necessarily detecting that something went wrong. It is understanding what happened.

Traditional scheduling tools are primarily concerned with triggering commands. Once a command has been started, its execution and output are often left to other mechanisms: system logs, redirected files, monitoring tools, or external scripts.

This creates a fragmented picture of what is happening.

A scheduler that manages the lifecycle of jobs should also provide a consistent way to inspect their execution history.

**Observability should not be an additional feature layered on top of job execution. It should be part of the execution model itself.**

## Two different kinds of information

When investigating a scheduled job, there are two fundamentally different questions:

- What happened during the execution?
- What did the job actually produce?

These questions require different kinds of information.

The first concerns execution metadata: when a job started, how long it ran, whether it succeeded, its exit code, and whether it was retried or interrupted.

The second concerns the output generated by the process: messages, diagnostic information, warnings, and errors.

Trying to represent both through a single logging mechanism is not particularly effective.

A large log file may contain plenty of information, but reconstructing the execution history from textual messages is difficult and error-prone.

Conversely, a database containing execution statuses cannot explain why a particular process failed.

cronx deliberately separates these responsibilities:

- SQLite stores execution history and runtime state.
- A shared log file collects the output of all job executions.

Each mechanism has a specific purpose, and neither needs to become a general-purpose observability platform.

## Execution history as structured data

The first requirement is to make every execution identifiable.

cronx records each execution attempt in a local SQLite database. Every attempt receives its own identifier and is associated with a job.

A simplified representation looks like this:

```text
runs
------------------------------------------------
id          INTEGER
job         TEXT
attempt     INTEGER
status      TEXT
started_at  TEXT
finished_at TEXT
exit_code   INTEGER
duration_ms INTEGER
error       TEXT
log_path    TEXT
```

The important design decision is that the database stores execution events as structured records rather than trying to reconstruct them from logs.

Each record captures the outcome of an attempt, including failures that occur before a process can even be started.

This distinction matters.

A process that exits with a non-zero status is different from one that cannot be created at all. A process terminated because it exceeded its timeout is different from one deliberately skipped because another execution was still running.

cronx represents these outcomes through explicit statuses:

- `scheduled`
- `running`
- `succeeded`
- `failed`
- `timed_out`
- `spawn_error`
- `skipped`

The history therefore describes what actually happened, not simply whether a command returned zero.

## An execution is not necessarily a single attempt

Retries introduce another interesting aspect.

Suppose a backup operation fails because a remote resource is temporarily unavailable. The scheduler retries the operation, and the second attempt succeeds.

If we only record the final outcome, the execution appears successful.

But this hides useful information: the first attempt failed, and the system needed a retry.

cronx records every attempt separately.

For example:

```text
ID  JOB     ATTEMPT  STATUS     DURATION  EXIT
12  backup  1        succeeded  1.2s      0
11  backup  2        failed     0.1s      1
10  backup  1        failed     0.1s      1
```

Each attempt has its own identifier, status, duration, and associated output.

This provides a more accurate picture of the execution lifecycle.

It also makes it possible to distinguish between a job that normally succeeds and one that frequently fails before eventually completing.

The distinction becomes particularly useful when investigating intermittent problems.

## Logs should remain simple

Structured execution history does not replace process output.

Applications already produce useful diagnostic information through standard output and standard error. There is little reason to invent another logging protocol just to collect it.

cronx captures both streams and appends them to a shared run log.

Every line is associated with four pieces of information:

- Timestamp.
- Job name.
- Run identifier.
- Process identifier.

For example:

```text
2026-10-06T03:00:00Z backup id=12 pid=4182 starting the backup
2026-10-06T03:00:01Z backup id=12 pid=4182 connecting to remote storage
2026-10-06T03:00:02Z backup id=12 pid=4182 backup completed
```

The run identifier is particularly important.

It connects the textual output to the corresponding structured execution record in SQLite.

The job name identifies the source, while the process identifier helps correlate messages with operating-system processes.

The result is a relatively simple logging model that remains compatible with ordinary command-line tools.

There is one shared file rather than a separate log file for every job or execution.

## History and logs are complementary views

Having two information sources is useful only if they can be inspected independently and related when necessary.

cronx provides separate commands for these purposes:

```bash
cronx status
```

Shows the latest outcome of every configured job and whether an execution is currently in progress.

```bash
cronx history backup
```

Displays the execution history of a specific job, newest first.

```bash
cronx logs backup
```

Displays the output generated by that job.

These commands answer different questions.

`status` provides a concise operational overview.

`history` explains how a job behaved over time.

`logs` provides the detailed information produced during execution.

The log command also supports filtering by time and following new output:

```bash
cronx logs --since 1h --follow
```

This is particularly useful when investigating a problem while the scheduler is running.

The command reads the log file directly. It does not need to open the SQLite database or modify runtime state.

This separation also means that the log can be inspected using ordinary tools such as `grep`, `tail`, and other command-line utilities.

## Persistence matters when the scheduler stops

Observability becomes more interesting when the scheduler itself fails.

Consider what happens if the machine loses power or the scheduler process is terminated unexpectedly while a job is running.

The process may disappear without the scheduler having an opportunity to record its final outcome.

If the execution history only contains completed jobs, the system may retain an incomplete or misleading picture of what happened.

cronx addresses this by recording an execution before starting the process.

The execution initially enters the `running` state. Once the process terminates, its final status and associated information are recorded.

If the scheduler is stopped unexpectedly, executions left in progress are identified when cronx starts again and closed as failed.

This is preferable to leaving stale `running` records indefinitely or silently assuming that the execution succeeded.

There is an important distinction between an orderly shutdown and an unexpected termination.

During a normal shutdown, cronx stops the running jobs, waits for them, and records their outcomes before exiting.

The recovery mechanism is primarily intended for situations where the scheduler was unable to complete that process.

The objective is not to pretend that every failure can be recovered automatically. It is to ensure that the recorded history remains truthful.

## Persistence without an external database

SQLite is a natural fit for this architecture.

It provides transactions, structured queries, and durable local storage without requiring a database server or an additional service.

For a single-machine scheduler, this is generally sufficient.

The database contains three main structures:

- `runs`: one record for every execution attempt.
- `job_state`: a compact representation of the latest outcome of each job.
- `scheduler_lease`: information identifying the scheduler currently controlling the state.

The `job_state` table is particularly interesting.

The execution history is the authoritative record of what happened, but frequently querying the entire history just to retrieve the latest outcome would be unnecessary.

A small state table provides a convenient representation of the most recent result.

The database also uses schema versioning and transactional migrations, allowing its structure to evolve without requiring users to recreate their execution history.

Timestamps are stored in UTC using RFC 3339, independently of the timezone used to calculate job schedules.

This avoids ambiguity when comparing executions produced on machines configured with different local timezones.

## Observability needs boundaries too

A history database and a log file can grow indefinitely.

This is not just a storage problem. It is also an operational design issue.

cronx provides two independent retention mechanisms.

The `[storage].max_runs` option limits the number of recent execution records retained for each job.

The `[logging].max_size` and `[logging].max_backups` options control log rotation.

These mechanisms have different responsibilities.

The history retention policy limits structured execution records, while log rotation limits the size of the output file.

The two can therefore be configured independently.

Importantly, retention is applied per job rather than globally. A frequently executed task cannot consume the entire history allowance and eliminate the records of less frequent jobs.

Without an explicit history limit, execution records are retained indefinitely. Similarly, the run log is not rotated unless a maximum size is configured.

This makes the storage behaviour explicit rather than imposing an arbitrary retention policy on every deployment.

## Conclusion

A job scheduler is often considered reliable when it executes commands at the right time.

But execution alone is not enough.

When something goes wrong, the ability to understand what happened becomes just as important as the ability to trigger the original task.

cronx approaches this problem by keeping execution history and process output separate, while connecting them through a common execution identifier.

SQLite provides structured and persistent information about every attempt. A shared log file preserves the output generated by the processes. A small command-line interface makes both accessible without requiring an additional monitoring infrastructure.

The interesting point is not the use of SQLite or the choice of a single log file. It is the decision to make observability part of the scheduler's basic responsibilities.

**A system is easier to operate when its history explains its behaviour, rather than forcing someone to reconstruct that behaviour from scattered log messages.**

This principle applies well beyond job schedulers. Any application that manages external processes, asynchronous operations, or long-running tasks benefits from treating execution history as a first-class part of its architecture.
